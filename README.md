# 装备仿真数据核对工具

关灯科技 · Python 开发工程师 · 二轮实战任务

## 目标与衡量

这东西是给装备仿真的调试人员用的。他们手上一般有两份数据：一份基准规则库，写着每个部件应该是多少、允许多大误差；一份本机解算输出，写着实际算出来多少。要干的活就是找出算错的那些部件。以前这一步靠人一行行对。

怎样算有用，我看三点：

1. 一条命令跑完就出结果，屏幕上得有进度条和靶盘，让不懂代码的主管也能一眼看出来"有几个部件有问题"。
2. 严重超标的部件要单独列一张清单。清单不能是黑盒，报告里每一条的超差倍数都能拿出来复核。
3. 米和毫米混着写的数据不用先手工整理，两份原始文件直接丢进去就能比。

核心指标只有一个：异常命中率 = 检出异常的部件数 ÷ 参与比对的部件总数。异常指的是"异常 + 严重超标"两档，缺失件不算命中（它是另一个维度的问题）。

## 怎么跑

无需额外依赖（仅 Python 3.11+ 标准库），不用 `pip install`。

```bash
python main.py
```

不带参数就跑仓库里自带的示例数据（`samples/baseline.csv` 和 `samples/result.csv`），差异报告写到 `diff_report.csv`。

换成自己的文件：

```bash
python main.py --baseline 基准库.csv --input 解算输出.csv --output 报告.csv
```

还有几个开关：`--no-color` 关彩色，`--no-anim` 关动画，脚本里调用的时候用得上。

`--html` 会额外产出一份自包含的 HTML 报告（不引外部资源，双击就能看，也可以直接丢到静态托管上当在线地址）：

```bash
python main.py --html report.html
```

在线演示页就是这么生成的，地址是 <https://jxjxjx666.github.io/guandeng-task/>。它由上面这条命令产出，纯静态文件（源码在 `docs/index.html`），由 GitHub Pages 直接从本仓库的 `docs/` 目录托管，不依赖后端，也没引任何 Web 框架。

输入是 CSV，两份文件的列不一样：

| 文件 | 必需列 |
|---|---|
| 基准规则库 | `part_id,x,y,unit,ref_value,limit` |
| 本机解算输出 | `part_id,x,y,unit,value` |

`unit` 写 `m` 或 `mm`，也认 `米`、`毫米`、`meter`、`millimeter` 这几种写法。表头大小写和首尾空格不影响。

拿仓库自带的示例数据来看。`samples/baseline.csv` 节选（第二行是毫米）：


## 做了什么

处理流程是：读两份 CSV，按 `part_id` 建索引，两边都先做单位归一化，然后逐个部件比对，最后落盘加展示。

单位这块，逐行读 `unit` 列，`mm` 除以 1000 换成米，`m` 原样留着，坐标统一到米之后再比。碰到不认识的单位直接报错，不猜系数。

比对做成双向的。以基准库为主表正向扫一遍，算 `diff = 实测 - 基准`，再算 `exceed_ratio = |diff| / limit`，据此分四档：`OK` 不到 1 倍，`ANOMALY` 到 1 倍，`SEVERE` 到 2 倍（就是清单里那些"严重超标"），`MISSING` 是基准里有、解算里没有。然后反向再扫一遍解算输出：有、但基准库里没有的部件记成 `EXTRA`（越界），单独报出来。这类部件往往代表算法算出了不该存在的东西，静默丢掉就是漏报。

输出三部分。报告写成 CSV 落盘，末尾附一行汇总；终端那边有彩色动效进度条和 ASCII 靶盘，再打两张清单（严重超标、越界）；加 `--html` 还会产出上面那份 HTML 报告。

靶盘是算出来的不是画死的：用程序画同心环，部件越离谱落点越靠外圈，靶心代表和基准完全一致，缺失的甩到靶外。这样改尺寸不会散架，也能把"偏了多少"直接摆在图上。

几个取舍说一下：

异常不用绝对差值分级，用超差比。因为各部件阈值量级差得远（示例里 0.2 和 1.0 差了 5 倍），拿绝对差横向比没有意义，也没法定"严重"这条线在哪儿。

靶盘宁可多写几十行代码去算坐标，也不贴一张写死的字符画。写死的图改一下尺寸就错位，而且表达不了"落在第几环 = 超差多少"这层信息。

比对用基准库做主表做左连接，再加一遍反向扫描。业务上首先要回答的是"基准要求的这些部件算得对不对"，所以由基准库定主表；但只查一个方向会把"多算出来的部件"整个吞掉，那是算法越界，属于要报的那一类，所以反过来也必须查。

第三方库能让终端更好看，`rich`、`colorama` 都能省不少事。这里刻意用标准库加 ANSI 手写，图的是换台机器不用装东西就能跑。演示的时候少一个失败点。

## 我的假设

任务书没规定数据格式和判定口径，下面这些是我自己拍的：

1. 数据格式按 CSV 来，列名就是上面那两组。之所以选 CSV，是因为它最通用，用表格软件就能打开验证。表头比较时大小写和空格不敏感。
2. 输入编码按 UTF-8 读，用 `utf-8-sig` 是为了兼容 Excel 导出的 BOM 头。
3. 单位只支持米和毫米，`unit` 列逐行标注。题面只提了"米与毫米混用"，所以厘米、微米这些一律当非法输入报错，不猜系数。
4. 单位列同时管这一行的坐标和数值，一行一个单位。要是实际数据里坐标和数值单位不一样，得拆成两列，见「已知风险」。
5. "数值"按一个标量处理，每个部件一个实测值对一个基准值，不是向量也不是多指标。
6. 主键是 `part_id`，两边都不允许重复。重复就直接报错，因为重复主键的对账结果本身就不可信，报错比闷头取一条安全。
7. 分级线定在超差比 1.0 和 2.0。题面说了"严重超标"但没给倍数，我取 2 倍当分界，写成了模块级常量 `SEVERE_RATIO`，想改一行就够。
8. 异常命中率的分母用"参与比对的部件总数"，包含缺失件，不是"有解算结果的部件数"。缺失本身也是要排查的信号。
9. 阈值给 0 的时候，只要有一点偏差就判 `SEVERE`，完全相等判 `OK`。这样既避开除零，也符合"阈值 0 就是零容差"的直觉。
10. 报告落盘用 CSV，方便后续处理和入库，汇总信息当注释行挂在文件末尾。
11. 解算里多出来、基准库没有的部件记成 `EXTRA`，单独报出来，不计入异常命中率的分子也不计入分母。它和"数值算错"是两类不同故障，混进同一个率里会互相稀释，两边都看不清楚。第一次提交时这类部件是被静默忽略的，本轮补上了。

## 没做什么及原因

30 分钟装不下题面给的全部诉求，下面是我主动砍掉的，按为什么砍排：

1. 在线地址只做到一份静态报告页，没做交互式的在线工具。也就是说网页上不能传自己的数据跑比对，只能看示例数据的结果。真正的在线工具要引后端、处理上传和并发，30 分钟里做不完，而且会把"本地一条命令可跑"这条硬要求复杂化。
2. 可交互的靶盘动画没做。比如逐发打靶、命中环闪烁。做的是静态靶盘加进度条动效。交互要上 `curses` 或第三方库，30 分钟里风险大过收益，演示时也容易手忙脚乱点错。
3. 坐标偏移没设阈值报警。偏移算出来了也写进报告了（`coord_offset_m` 列），但没给"偏移超过多少算异常"定线。题面对坐标只要求"识别并转换"，比对的主体是数值。先保证换算是准的，报警留给下一轮。
4. 没做多指标扩展。见假设 4 和 5，先跑通题面写明的场景。
5. 没做配置文件。阈值、分级、颜色要么写死在代码里，要么走命令行开关。30 分钟里多加一层配置，只会多一个出错的地方。
6. CI 和打包没碰。不在验收点上。

先做后做的顺序是这么定的：最先做「单位归一化 + 比对 + 报告落盘」这条主干。它是这个工具唯一不可替代的功能，没有它整个东西没有任何意义，靶盘做得再花也换不来一个正确的比对结果。主干跑通了才去补终端呈现。

## 已知风险

1. 单位列是按行的，不是按列的。如果哪个部件的基准值也带单位（比如 `ref_value=20mm`），现在的代码会把它当无量纲数直接比，会静默算错。这是最该先修的。
2. `limit` 或 `ref_value` 不是数字时，`float()` 抛的 `ValueError` 会被 `main` 接住，以退出码 3 结束并告诉你是哪份文件缺哪列，但不会告诉你是哪一行。数据量大的时候不好定位。
3. 越界只按 part_id 判。解算里多出一个部件编号会被报成 `EXTRA`，但要是编号对得上、只有坐标落到允许区域之外，现在不会报。那是另一类越界，得单独定判据，本轮没做。
4. `SEVERE_RATIO = 2.0` 是我拍的。真实业务里"严重"的界可能得按部件类型分别定，现在是一刀切。
5. 靶盘的落点是示意，不是真实投影。角度按部件顺序均分，不是按坐标算的。所以它能表达"有几个离谱的、离谱到什么程度"，但读不出部件的实际方位。演示时要是有人问"这个点在靶上什么位置"，得先讲清楚。
6. 圆只是近似。字符单元的高宽比大概 2:1，代码用"纵向距离乘 2"来凑。换个非等宽字体或者比例不对的终端，靶盘会变成椭圆。
7. 彩色动效没在 Windows 原生 cmd 上验证过。ANSI 转义在 Git Bash、Windows Terminal、Linux 终端下都正常，老版 cmd 可能要手动开 VT 支持。非交互终端（输出重定向到文件）会自动关掉颜色和动画。
8. 没测过大数量级。7 行示例数据下耗时可忽略。比对是 O(n) 的字典查找，靶盘渲染是 O(宽×高) 跟部件数无关。上万行没实测过。
9. 浮点比较没用容差。`diff` 直接做减法，理论上 `0.1+0.2` 这类精度问题会让边缘情况差一个 ULP 就跨过分级线。实际数据是仪表读数（有限小数），风险不高，但确实没做防御。

## 再给 2 小时我会怎么做

按优先级排：

1. 先修风险 1 和 2。单位和数值拆成两列独立标注；错误信息带上行号和原始值。
2. 给坐标配上判据。一是坐标偏移的阈值报警（现在只算偏移不报警），二是"坐标落到允许区域之外"这类越界——现在只按 part_id 判越界，编号对得上的坐标异常还报不出来（见「已知风险」第 3 条）。
3. 加 `--format json` 输出，让工具能被别的系统消费。再写一个 `--watch` 模式轮询目录，解算一出新结果就自动比一遍。
4. 把分级规则外置成一个小 JSON 配置，按部件前缀定不同阈值，让业务同事自己能调，不用改代码。
5. 在线地址现在是静态报告页，只能看示例数据的结果。下一步做成能上传自己数据跑比对的交互式页面，这样才算是真的在线工具。
6. 性能方面改成流式读取（`csv.reader` 逐行 yield），不一次读进内存，再补个百万行的压测。
7. 测试还能再强一层。现在补上了 `tmp_path` 的集成测试，但还没端到端跑 CLI（真正执行 `main.py` 再断言退出码和落盘文件），也缺一个"故意写坏单位/写坏列名"的模糊测试。

## 本轮改了什么

第一版在时限内交掉之后，我又补了一轮。这三件事都是第一版里自己写下的不足，不是新加的花样：

**1. 比对改成双向，补上越界部件（`EXTRA`）。**
第一版只查了一个方向：基准库有、解算没有的报 `MISSING`，反过来解算多出来的部件被静默丢掉了。那是漏报，而且漏掉的恰恰是算法越界这种最该报的情况。现在反向也扫一遍，多的部件记成 `EXTRA`，报告里跟 `MISSING` 并列，终端单独打一张清单，靶盘上给一个 `▲` 的落点。命中率的口径没动，分子仍然只算异常和严重超标，越界单独报数——它跟"数值算错"是两类故障，混在一起互相稀释，两边都看不清。

**2. 补上读 CSV 那条链路的测试。**
第一版 13 条测试全是直接构造 `Baseline` / `Sample`，而这两个类的 `x_m` 字段本身就是米，`to_meters()` 从头到尾没被走到过一个字节。也就是说，把 `load_baseline` 里那句 `to_meters(row["x"], unit)` 换成 `float(row["x"])`，13 条测试照样全绿，但真实数据会全部算错。

这不是推理，是实测过的：改完那行再跑，原来的 13 条 **13 passed**，新加的 8 条里挂掉 3 条（`test_集成_基准库读入时毫米真的被换算` 断言 1.5 拿到 1500，`test_集成_混单位端到端偏移为零` 偏移变成 2912.56）。现在测试总数 21 条。同时把原来那条测试里写错的注释（`# 1500mm/2500mm`，代码里根本没有 1500 这个数）也改掉了。

**3. 加了在线地址。**
这是任务书列的加分项。做法是给工具加了一个 `--html` 开关，跑完顺手产出一份自包含的 HTML 报告，再把这份静态文件发布出去。没引任何 Web 框架，也没加后端——工具本身还是"本地一条命令可跑"，在线页只是它的一个可选产物。

对应的 README 改动：`怎么跑` 补了 `--html` 用法，`做了什么` 改成双向比对，`我的假设` 第 11 条重写了命中率口径，`没做什么及原因` 第 1 条从"在线地址没做"改成"只做到静态页、没做交互式在线工具"，`已知风险` 第 3 条从"缺失只查一个方向"换成"越界只按 part_id 判、坐标越界仍未覆盖"。
