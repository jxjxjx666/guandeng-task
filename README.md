# 装备仿真数据核对工具（guandeng-task）

关灯科技 · Python 开发工程师 · 二轮实战任务

## 目标与衡量

**为谁解决什么问题**：为装备仿真系统的开发/调试人员，比对「本机解算输出」和「基准规则库」两份数据，把算错了的部件挑出来，替代人工逐行核对。

**怎样算有用**：

1. 主管要向客户演示，**一条命令跑完、屏幕上有完整的视觉呈现**（打靶进度条 + ASCII 靶盘 + 汇总），不需要懂代码也知道结果。
2. 能自动挑出**严重超标**的部件，并且这个清单是可信的 —— 报告里的 `exceed_ratio` 列可以逐条复核。
3. 混合单位的数据不需要人工预处理，**直接把两份原始文件丢进去就能比**。

**核心指标**：异常命中率 = 检出异常（异常 + 严重超标）部件数 ÷ 参与比对部件总数。

## 怎么跑

**无需额外依赖（仅 Python 3.11+ 标准库）**，不需要 `pip install`。

```bash
python main.py
```

不带参数会直接跑仓库里自带的示例数据（`samples/baseline.csv` + `samples/result.csv`），并把差异报告写到 `diff_report.csv`。

指定自己的文件：

```bash
python main.py --baseline 基准库.csv --input 解算输出.csv --output 报告.csv
```

其他开关：`--no-color`（关彩色）、`--no-anim`（关动画，适合脚本里跑）。

**输入格式**（CSV，表头大小写和首尾空格不敏感）：

| 文件 | 必需列 |
|---|---|
| 基准规则库 | `part_id,x,y,unit,ref_value,limit` |
| 本机解算输出 | `part_id,x,y,unit,value` |

`unit` 是 `m` / `mm`（也接受 `米`/`毫米`/`meter`/`millimeter` 等写法）。

**示例（仓库自带数据，可直接复现）**：

输入 `samples/baseline.csv`（节选，注意第 2 行是毫米）：

```
part_id,x,y,unit,ref_value,limit
P001,1.000,2.000,m,10.0,0.5
P002,1500,2500,mm,20.0,1.0
P005,5.000,6.000,m,25.0,0.5
```

输入 `samples/result.csv`（节选，P002/P005 改用米/毫米混着写）：

```
part_id,x,y,unit,value
P001,1.000,2.000,m,10.2
P002,1.5,2.5,m,24.5
P005,5000,6000,mm,25.1
```

输出 `diff_report.csv`（这就是"持久化到本地文件"的差异报告）：

## 做了什么

1. **读两份 CSV** → 按 `part_id` 建立索引，两份数据都先做单位归一化。
2. **单位换算**：逐行读 `unit` 列，`mm` ÷ 1000 换成米，`m` 原样保留，坐标统一到米之后再比较。认不出的单位直接报错，不猜。
3. **逐部件比对**：以基准库为主表，算 `diff = 实测 - 基准`，再算 `exceed_ratio = |diff| / limit`，据此分四级：`OK`（<1 倍）、`ANOMALY`（≥1 倍）、`SEVERE`（≥2 倍，即"严重超标"）、`MISSING`（基准里有、解算没有）。
4. **输出**：报告写成 CSV 落盘（含汇总行）；终端打彩色动效进度条 + ASCII 靶盘；打印严重超标清单。
5. **终端呈现**：靶盘用程序算坐标画同心环，不是贴死的字符串 —— 部件越离谱落点越靠外环，靶心代表与基准完全一致；缺失件甩到靶外。

**关键取舍**：

- **异常用「超差比」而不是绝对差值**分级。因为各部件阈值量级不同（0.2 和 1.0 差 5 倍），用比值才能横向比较、才能定"严重超标"这条线。
- **ASCII 靶盘用程序生成而不是硬编码画布**。硬编码的靶图改了尺寸就散架，而且没法表达"落在第几环 = 超差多少"这层信息。
- **以基准库为主表做左连接**，而不是双向全连接。业务上要回答的是"基准要求的这些部件，算出来对不对"，基准里没有的部件不该拉进来。
- 有第三方库（`rich`/`colorama`）能让终端更好看，但**刻意用标准库 + ANSI 手写** —— 换台机器不用装任何东西就能跑，演示时少一个失败点。

## 我的假设

任务书没有规定数据格式和判定口径，以下是我自己拍的板：

1. **数据格式假定为 CSV**，列名固定为上面那两组。给的是两份"数据"，我选了最通用、最好用表格软件打开验证的格式。表头比较时大小写和首尾空格不敏感。
2. **输入编码假定为 UTF-8**（用 `utf-8-sig` 读，兼容 Excel 导出的 BOM 头）。
3. **单位只支持米和毫米两种**，`unit` 列逐行标注。题面只提到"米与毫米混用"，所以其他单位（厘米、微米）一律视为非法输入报错，而不是猜一个系数。
4. **单位列同时作用于该行的坐标和数值**（一行一个单位）。如果实际数据里坐标和数值单位不同，需要拆成两列，见"已知风险"。
5. **"数值"指一个标量**（每个部件一个实测值对一个基准值），不是向量或多指标。
6. **主键是 `part_id`**，且两边都不允许重复 —— 重复直接报错，因为重复主键的对账结果不可信，报错比静默取一条安全。
7. **分级阈值**：`exceed_ratio ≥ 1.0` 为异常、`≥ 2.0` 为严重超标。题面只说"严重超标"没给倍数，我取 2 倍作为分界，并把它提成模块级常量 `SEVERE_RATIO`，一行就能改。
8. **异常命中率的分母是"参与比对的部件总数"**（含缺失件），不是"有解算结果的部件数"。因为缺失本身也是要排查的异常信号。
9. **阈值为 0 时**：只要有一丝偏差就判 `SEVERE`，完全相等判 `OK`。这样避免除零，也符合"阈值 0 = 零容差"的直觉。
10. **报告用 CSV 落盘**，方便二次处理和入库；汇总信息作为注释行附在文件末尾。
11. **解算输出里多出来的部件（基准库里没有）不参与统计**，见下一条。

## 没做什么及原因

30 分钟装不下题面给的全部诉求，以下是我主动砍掉的，按"为什么砍"排列：

1. **没装 Web 界面 / 在线地址**。任务书把这列为加分项。砍掉的原因：这是最花钱的一项（要引入 Web 框架、前端、部署），而"本地一条命令可跑"是硬要求，先把硬要求做扎实。终端呈现已经能覆盖"看起来完整连贯"这个诉求。
2. **没做可交互的动画靶盘**（比如逐发打靶、命中的环闪烁）。做了不可交互的静态靶盘 + 带颜色的进度条动效。原因：交互需要 `curses` 或第三方库，30 分钟内风险大于收益，而且演示时反而容易点错。
3. **没处理"坐标偏移超标"的报警**。坐标偏移算出来了、也写进报告了（`coord_offset_m`），但没给它设阈值报警。原因：题面的比对要求是"比对部件数值"，坐标换算只要求"识别并转换"。先保证换算正确，报警留到下一轮。
4. **没做多指标 / 多单位制扩展**。见假设 4、5，先跑通题面写明的场景。
5. **没做配置文件**。阈值、分级、颜色都写在代码里（或命令行开关）。30 分钟里多加一层配置只会多一个出错的地方。
6. **没写 CI / 打包**。不在验收点上。

**先做什么、为什么**：先做「单位归一化 + 比对 + 报告落盘」这条主干，因为它是数据核对工具的**唯一不可替代的功能** —— 没有它，这个工具没有任何意义；打靶动效做得再炫也换不来一个正确的比对结果。主干跑通之后才做终端呈现。

## 已知风险

1. **单位列是"按行"的，不是"按列"的**。如果某个部件连基准值也带单位（比如 `ref_value=20mm`），当前代码会把它当无量纲数直接比 —— 会静默算错。这是最需要优先修的。
2. **`limit`/`ref_value` 非数字时**：`float()` 抛的 `ValueError` 被 `main` 捕获，会以退出码 3 结束并打印是哪份文件缺哪列，但**不会指出是哪一行**。数据量大时定位麻烦。
3. **只有 `MISSING` 一个方向的缺失检测**。基准库里没有、解算输出里多出来的部件被静默忽略。如果实际需求要报"多算了"，现在的工具答不出来。
4. **`SEVERE_RATIO = 2.0` 是我拍的**。真实业务里"严重"的界可能要按部件类型分别定，现在是一刀切。
5. **ASCII 靶盘的落点是"示意"不是"真实投影"**。角度是按部件顺序均分的，不是按坐标算的 —— 所以靶盘能表达"有多少个离谱的、离谱到什么程度"，**不能**用来读部件的实际方位。如果演示时有人问"这个点在靶上哪个位置"，要提前讲清楚。
6. **圆形只是近似**。字符单元高宽比大约 2:1，代码用"纵向距离乘 2"来补偿。换成非等宽字体或比例不对的终端，靶盘会变成椭圆。
7. **彩色动效没有在 Windows 原生 cmd 上验证过**。ANSI 转义在 Git Bash、Windows Terminal、Linux 终端下都正常；老版 cmd 可能需要开 VT 支持。非交互终端（重定向到文件）会自动关掉颜色和动画。
8. **没有大数据量验证**。7 行示例数据下耗时可忽略；比对是 O(n) 的字典查找，但靶盘渲染是 O(width×rows)，与部件数无关。上万行数据没实测过。
9. **浮点比较没有用容差**。`diff` 直接用减法，理论上 `0.1+0.2` 这类精度问题可能让边缘 case 差一个 ULP 就跨过分级线。实际数据是仪表读数（有限小数），风险低，但没有做防御。

## 再给 2 小时我会怎么做

1. **修风险 1 和 2**（最高优先）：单位和数值拆成两列独立标注；错误信息带上行号和原值。
2. **补"双向缺失"检测**：加 `EXTRA` 状态，报出解算输出里多出来的部件；再补上坐标偏移的阈值报警。
3. **加一个 `--format json` 输出**，让工具能被别的系统消费；再写一个 `--watch` 模式轮询目录，解算一出新结果就自动比。
4. **把分级规则外置成一个小 YAML/JSON 配置**（按部件前缀定不同阈值），让业务同事自己能调，不用改代码。
5. **试接一个真·在线地址**：用标准库 `http.server` 起一个只读页面展示最近一次报告，不动现有 CLI 结构。这样能拿到任务书的加分项。
6. **性能与健壮性**：改成流式读取（`csv.reader` 逐行 yield）而不是一次读进内存；补上百万行的压测。
7. **测试补强**：加 `pytest` 的 `tmp_path` 跑端到端 CLI 测试（现在只测了纯函数），再加一个"故意写坏单位"的模糊测试。
